## 📋 一句话定义

**GitHub = 一个「文件协作 + 历史追溯」的云平台**。

把文件放上去之后：
- ✅ 任何改动都有记录（谁改的、什么时候改的、改了啥）
- ✅ 多人可以同时改，自动合并
- ✅ 改坏了可以一键回滚
- ✅ 别人可以提建议（评论、修改）

它原本是给程序员写代码用的，但**协作 + 历史追溯这两个能力，对任何需要多人协作的文件都很有用**——包括运营的文档、资料、模板。

## 🤔 跟网盘/邮件附件有啥区别

| 场景 | 网盘（百度网盘/坚果云） | 邮件附件 | **GitHub** |
|------|------------------|---------|-----------|
| 多人改同一份文件 | ❌ 互相覆盖、谁后改谁说了算 | ❌ 一份份传，版本混乱 | ✅ 自动合并、有冲突提示 |
| 改坏了一键回滚 | ❌ 自己手动备份 | ❌ 找历史邮件 | ✅ 一键回到任意历史版本 |
| 知道谁改了什么 | ❌ 不知道 | ❌ 邮件太多找不到 | ✅ 每次改动都有记录 |
| 提建议/讨论 | ❌ 没评论功能 | ❌ 邮件来回 | ✅ 在文件旁边直接评论 |
| 权限控制 | ✅ 但配置复杂 | ❌ 邮件收件人能看就行 | ✅ 细粒度（读/写/管理） |

**简单说**：网盘/邮件适合「分发」（一人写、多人看），GitHub 适合「协作」（多人改一份东西）。

## 🎯 运营会用 GitHub 的几个场景

### 场景 1：团队知识库
把团队的 SOP（标准操作流程）、模板、案例库放到 GitHub：
- 改一处，全员看到最新版本
- 谁的修改被采纳、谁提的建议，历史清清楚楚
- 新人入职直接 clone 整个知识库

### 场景 2：协作写文档
多人一起写一份文档（产品介绍、市场报告、活动方案）：
- 每人负责一个章节，Codex 帮合并
- 评论直接在文档旁边提
- 改坏了随时回滚

### 场景 3：存运营资料并追踪变更
比如「每周竞品监控报告」：
- 每周更新一次，历史版本都在
- 对比本周和上周有什么变化（diff）
- 老大随时能 review

### 场景 4：跟 Codex 配合
这是本手册的重点：
- 把团队资料放到 GitHub，Codex 直接读 GitHub 上的最新版本
- Codex 生成的报告直接提交回 GitHub，团队成员都能看到
- 用 GitHub Issues 跟 Codex 提需求、追踪 Codex 跑的任务

### 场景 5：模板库共享
把团队常用的 prompt 模板、Excel 模板、邮件模板放到 GitHub：
- 模板更新了，所有人都能拉到最新版
- 团队成员可以提 PR（修改建议）改进模板

## 📖 必须知道的 5 个 GitHub 概念

运营不需要懂所有 GitHub 概念，但下面 5 个要知道：

### 1. 仓库（Repository）
**类比**：一个项目文件夹
**是什么**：存放一个项目所有文件的地方，每个项目对应一个仓库
**例子**：`codex-for-ops` 这个仓库里，存放着这本手册的所有文件

### 2. 提交（Commit）
**类比**：保存一个版本
**是什么**：每次你改了文件，点击「提交」就保存了一个新版本
**特点**：每次提交都有说明（commit message），告诉别人你改了什么
**例子**：
```
✅ 好的提交说明：「更新 5 月份活动数据」
❌ 不好的提交说明：「改了一下」、「fix」、「update」
```

### 3. 分支（Branch）
**类比**：Word 文档的「修订模式」
**是什么**：在原文件基础上开一个「副本」，你改完了再合并回去
**为什么要用**：避免你改坏了影响别人，或者多人同时改互不干扰
**例子**：
- 主分支（main）= 最终对外发布的版本
- 你的分支（小王的活动复盘）= 你的草稿
- 改完了提 PR → 合并回 main

### 4. PR（Pull Request，合并请求）
**类比**：把草稿发给主编审核
**是什么**：告诉别人「我改完了，请求把我的改动合并到主版本」
**特点**：合并前别人可以评论、要求修改，**通过审核才合并**
**例子**：
```
小王提了 PR：把"6 月活动复盘"加到运营文档里
  → 主编评论：第 3 段的数据需要核实
  → 小王修改 → 主编审核通过 → 合并到主版本
```

### 5. Issue（议题）
**类比**：工单 / 反馈单
**是什么**：用来追踪问题、需求、任务
**特点**：每条 Issue 有评论、状态（待处理/处理中/已完成）、负责人
**例子**：
```
Issue #42：把竞品分析模板升级到 V2 版
  → 状态：待处理 → 处理中（@小王）→ 已完成
```

## 🤔 运营一定要会 GitHub 吗？

**不一定**。看你团队怎么用：

| 团队规模 | 推荐使用方式 |
|---------|----------|
| 1-3 人 | 微信/钉钉共享文件夹就够了 |
| 4-10 人 | 强烈推荐用 GitHub 协作（哪怕只用来存文档） |
| 10+ 人 | 不用 GitHub 等着崩——文档一定会乱 |

**给运营团队的建议**：
- **先会用 GitHub 网页**（看文件、看历史、看评论）—— 这就够日常用了
- **偶尔学一下 GitHub Desktop**（图形化上传/下载文件）—— 想修改时用
- **命令行不用学**——交给开发者或 Codex

1. **GitHub = 文件协作 + 历史追溯的云平台**，不只是程序员用
