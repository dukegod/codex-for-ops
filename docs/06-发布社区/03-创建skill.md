# 3. 创建 Skill：把方法打包成可复用

> 把方法论变成别人能一键装上的 Skill

## 🎬 场景故事

小陈的资源整合完了，有了一份 `method-30min-competitor-weekly-report-v1.md`。

接下来她要做的是：**把这份方法论打包成 Skill**，让其他用户能「一键安装到自己的 Codex 里直接用」。

**这章就是讲怎么打包**。

## 🎯 你将学到

- Skill 的标准格式（小红书 RED Skill 兼容规范）
- 怎么用 Codex 自动生成 SKILL.md
- Skill 的关键要素（名字、描述、Prompt、注意事项）
- 怎么测试 Skill 能不能用

## 📋 Skill 的标准结构

不管你是给 Codex 用还是发布到小红书，**Skill 的目录结构都长这样**：

```
my-skill-name/                  # Skill 文件夹（用 kebab-case 命名）
├── SKILL.md                    # ⭐ 必需：Skill 定义文件
├── scripts/                    # 可选：辅助脚本
│   └── helper.py
├── references/                 # 可选：参考资料
│   └── examples.md
└── assets/                     # 可选：资源文件
    └── template.png
```

**最简版本只要一个 SKILL.md 文件就够**。其他目录是进阶用的。

## 📝 SKILL.md 的完整格式

### 模板（直接复制）

```markdown
---
name: 30min-competitor-weekly-report
description: |
  30 分钟搞定竞品周报。读取指定文件夹的 3-5 家竞品资料（PDF/网页截图/MD），
  自动生成结构化的周报 markdown，包括对比表、趋势分析、下周关注点。
  适用于每周一上午的运营周报场景。
---

# 30 分钟搞定竞品周报

## 使用场景

- 周一上午做本周竞品监控
- 月底做季度竞品分析
- 新产品发布前的竞品 baseline
- 给老板做临时竞品简报

## 不适用场景

- ❌ 需要精确数字（Codex 可能算错）
- ❌ 需要法律/合规审核的对外报告
- ❌ 公司内部未公开的产品信息

## 输入要求

### 必需资料

在指定文件夹里放：
- 3-5 家竞品的最新资料（PDF/网页截图/MD 文件）
- 命名建议：`competitor-<公司名>-<日期>.pdf`

### 可选资料

- 上周的周报（用于对比变化）
- 公司内部关注点清单（让 Codex 重点分析）

### 文件夹结构

```
weekly-report-input/
├── competitor-A-2026-06-29.pdf
├── competitor-B-2026-06-29.pdf
├── competitor-C-2026-06-29.md
└── last-week-report.md  # 可选
```

## 完整步骤

### Step 1：准备资料文件夹

把本周竞品资料放进一个文件夹。

### Step 2：新建 Codex 任务

1. 打开 Codex 桌面端
2. 点 + New Task
3. 选刚才的资料文件夹
4. 在输入框粘贴下面的「完整 Prompt」
5. 选安全模式：🟡 自动编辑（日常推荐）
6. 点 Start Task

### Step 3：等 Codex 跑（约 10-15 分钟）

Codex 会：
1. 读所有竞品资料
2. 提取关键信息
3. 生成对比表
4. 输出周报 markdown

### Step 4：审阅 + 微调

打开生成的周报：
- 核对关键数字（销售额、用户数等）
- 调整不符合品牌调性的措辞
- 补充 Codex 漏掉的洞察

## 完整 Prompt

```
读取这个文件夹里所有竞品资料（PDF/MD/截图），生成本周竞品周报。

要求：

1. 提取每个竞品的以下信息：
   - 公司名 / 产品名
   - 核心功能更新
   - 营销动作
   - 用户反馈（如果有）
   - 定价变化

2. 输出 markdown 格式的周报，包含：
   - 本周概览（3-5 句话总结）
   - 竞品动态对比表（markdown 表格）
   - 重点关注（哪个竞品动作最大、为什么）
   - 我们的应对建议（至少 3 条）
   - 下周关注点

3. 写作风格：
   - 数据说话，避免形容词
   - 短句为主
   - 用 markdown 表格做对比

4. 文件名：competitor-weekly-report-YYYYMMDD.md

5. 直接输出，不要让我再追问
```

## 预期输出

生成的 markdown 文件长这样：

```markdown
# 竞品周报 2026-06-30

## 本周概览
本周 3 家竞品都有动作，重点关注 A 的新功能发布...

## 竞品动态对比表

| 维度 | 竞品 A | 竞品 B | 竞品 C |
|------|-------|-------|-------|
| 核心更新 | ... | ... | ... |
| 营销动作 | ... | ... | ... |
| ...

## 重点关注
竞品 A 发布了 XX 功能，跟我们 Q3 路线图重合...

## 应对建议
1. ...
2. ...
3. ...

## 下周关注点
- 竞品 B 的发布会
- ...
```

## 注意事项

### 🚨 数据准确

- 所有数字必须自己再算一遍（Codex 可能算错）
- 引用必须能溯源到原文

### 🚨 敏感信息

- 不要喂客户隐私数据
- 不要写未公开的内部数据
- 公司内部代号要做脱敏

### ⚠️ 风格统一

- 用 markdown，不用富文本
- 表格用 markdown 格式
- 不用 emoji 装饰（除非风格需要）

### ⚠️ 常见坑

1. **资料太多**：5 家以上时先分批，让 Codex 跑完再合并
2. **格式混乱**：先整理成统一格式（建议先转 markdown）
3. **跑偏方向**：用 prompt 加约束「只关注 X，不要涉及 Y」

## 作者信息

- 作者：小陈
- 适用版本：Codex 桌面端 v1.0+
- 最后更新：2026-06-30
```

### 模板的关键要素

每个 SKILL.md 必须包含这 7 个部分：

| 要素 | 作用 | 没它会怎样 |
|------|------|----------|
| **Frontmatter**（YAML） | 机器可读的元数据（name + description） | Skill 不能被搜索到 |
| **使用场景** | 告诉读者什么时候用 | 读者不知道适不适合自己 |
| **不适用场景** | 划清边界 | 读者乱用，效果差 |
| **输入要求** | 告诉读者要准备什么 | 读者跑不起来 |
| **完整步骤** | 操作 SOP | 读者不知道怎么做 |
| **完整 Prompt** | 可直接复制 | 读者要自己写 prompt |
| **注意事项** | 避坑指南 | 读者踩坑 |

**7 个都写齐，Skill 才完整**。

## 🚀 用 Codex 自动生成 SKILL.md

如果你已经有了「结构化方法论」（[Step 2: 资源整合](02-资源整合.md)），让 Codex 帮你转成 SKILL.md：

### 创建 Codex 任务

1. **+ New Task**
2. 选**资源整合的输出文件夹**（包含 method-...md 的那个）
3. 选安全模式：🟡 自动编辑
4. 输入下面的 prompt

### 完整 prompt（直接复制）

```
读取这个文件夹里的 method-30min-competitor-weekly-report-v1.md，
把它转成符合 Codex Skill 标准格式的 SKILL.md。

要求：

1. 输出文件名：SKILL.md
2. 保存到当前文件夹
3. SKILL.md 必须包含：
   - Frontmatter（name + description）
   - 使用场景
   - 不适用场景
   - 输入要求（含文件夹结构示例）
   - 完整步骤（5-8 步）
   - 完整 Prompt 模板（可直接复制）
   - 预期输出（markdown 示例）
   - 注意事项（含常见坑）
   - 作者信息

4. 写作要求：
   - 简洁、口语化
   - 步骤清晰，每步说清楚做什么
   - Prompt 完整可粘贴，不要片段
   - 常见坑至少 5 条
   - 总长度控制在 2000-3000 字

5. Skill 命名规范：
   - 用 kebab-case（短横线连接）
   - 名字要能看出用途
   - 例：30min-competitor-weekly-report
```

### 等 Codex 跑（约 5 分钟）

Codex 会读你之前的方法论文件，输出一个符合规范的 SKILL.md。

## 🧪 测试 Skill

**发布之前必须自己测试一遍**：

### 测试 1：本地安装测试

1. 把 Skill 文件夹复制到 `~/.codex/skills/`
2. 重启 Codex
3. 在 Codex 里点 `/skills`
4. 找到你刚装的 Skill，点一下
5. 看 Codex 能不能正确理解任务

### 测试 2：换个人测试

让你同事按 Skill 里的步骤跑一遍：
- 不给任何额外说明
- 看他们能不能照着做
- 卡住的地方 = 你 Skill 没写清楚的地方

### 测试 3：换资料测试

用一份**你没准备过的资料**，让同事跑 Skill：
- 如果能跑通 → Skill 通用性 OK
- 如果跑不通 → 你的 Skill 太依赖特定资料

**3 个测试都通过，Skill 就可以发布了**。

## 🎯 Skill 命名的艺术

好的 Skill 名字要做到：

| 标准 | 例子 |
|------|------|
| **能看出用途** | `30min-competitor-weekly-report` ✅ |
| **能看出时长/规模** | `5min-quick-summary` ✅ |
| **kebab-case**（短横线连接） | ❌ `30MinCompetitorWeeklyReport` |
| **不要太长**（≤ 30 字符） | ❌ `30-min-complete-competitor-weekly-report-generator-with-ai` |
| **不包含公司内部代号** | ❌ `acme-product-spec-review` |

**好名字 vs 坏名字**：

```
✅ 30min-competitor-weekly-report
✅ meeting-summary-v2
✅ weekly-excel-cleanup
✅ user-feedback-classifier

❌ weekly_report_final_v2.md  （带扩展名、版本号太多）
❌ 我们公司的竞品分析       （中文 + 太具体）
❌ xiaowang_method_01         （带人名）
```

## ⚠️ 创建 Skill 的常见错误

### ❌ 错误 1：Skill 写得太复杂

试图把所有功能都塞进一个 Skill，结果没人看得懂。

**解法**：一个 Skill 只解决一个具体问题。要做复杂的事就组合多个 Skill。

### ❌ 错误 2：Prompt 写得像散文

Prompt 里写「请帮我仔细分析一下这个资料，看看有什么值得关注的地方」——这种没用的 prompt。

**解法**：Prompt 要**具体到字段**、**具体到格式**。

### ❌ 错误 3：没写「不适用场景」

读者不知道什么情况下不能用，乱用后效果差，给差评。

**解法**：必须明确写「不适用场景」。

### ❌ 错误 4：没测试就发布

发出去别人跑不通，口碑会差。

**解法**：发布前至少 3 个人测试过。
